### How we work (sessions, models, reviews, documents, merging, releases)

- **D470** (with D221, D332, D117, D341, D148, D468): How the sessions coordinate, so only what needs Kyler reaches him. **Review:** Kyler never reviews a PR or a line of code, except for design, taste or human-facing behaviour. Claude reviews code: the milestone session reviews every PR's diff before it merges (correctness, scope, ownership of files); its own PRs that touch the core or the water get a review from a fresh sub-agent that didn't write them. Theme rounds by Claude Code sessions land as real PRs into dev, re-pin included (D148), not as investigations with a patch to adopt; if two theme PRs collide on pins, the milestone session re-pins the later one itself. Codex stays on investigation branches, adopted on Kyler's yes. **Reports** to Kyler are short: at most about eight lines (what changed, what's still wrong, the numbers a decision needs) plus the sheet, capture or link; detail goes in the files; every session posts the same short report on its PR, or on the Coordination issue if there's no PR, as well as in its chat. **Labels** (hold: never merge; needs-kyler: waiting on Kyler's eye, never merge while on; approved: Kyler approved the human-facing result), each session setting them on its own PRs. The milestone session merges, through the merge queue, any green PR that isn't hold or needs-kyler; a PR that changes what a player sees, hears or feels (a theme, a force, the page, sound, wording) needs approved; a PR with nothing human-facing (internals, CI, Rust ports, cleanup, docs, investigations) merges on review and green CI. **The Coordination issue** (#236, pinned) carries messages between Claude Code sessions; each comment starts "To milestone:", "To page:", "To renderer:" or "To <session name>:"; every Claude Code session reads it when it starts a task, before it pushes and when it finishes, and answers there. Codex doesn't use it; the milestone session reads Codex's branches. **The line.** Settled between sessions without Kyler: merge order, holds, rebases, re-pins, CI failures (whoever's change broke it fixes it), a core function another session needs that changes nothing a player sees or hears, ordering on overlapping files within the ownership rules, merging investigations. Kyler only: anything a player sees, hears or feels; a new direction or scope; a decision that constrains future work; adopting a Codex investigation into the product; releases; probe batches (D117); starting a session or anything else that spends usage; a disagreement sessions can't settle; anything a session is unsure about. Those get needs-kyler and a ping (D332). Everything that needs Kyler carries needs-kyler on GitHub, so one list shows it all: with a PR, the PR gets the label; without one (a question, a trade, a probe batch request, a sitting), the session opens a small issue, its question in a few lines, labelled needs-kyler, and closes it once Kyler has answered; the milestone session labels a Codex investigation PR needs-kyler when it's ready for Kyler's adoption verdict. **Pings** also go to his phone: `tools/notify.ps1` posts to ntfy when `%USERPROFILE%\.dgm-ntfy-topic` exists (the topic is never printed, logged or committed); still only when his attention is needed, never for progress. **Numbers:** from now on a decision gets a number only when it's a rule that constrains future work; model choices, which session does what, Kyler's verdict on one round and "adopt this patch" go in STATUS or the Progress log, unnumbered; numbers already handed out stay. Kyler, 2026-10-04.
